# 090c:0768 capture investigation — 2026-10-18

The submitted Wavlink adapter uses the same observed JPEG display protocol as
smid's 090c:0760 device. This is strong evidence that a port can reuse the frame
encoder and packet builder. Clayton subsequently passed the exact VA-API
pipeline on his HD 520 and reported successful USB/desktop operation on October
21 (see the follow-ups below). Longer-term stability remains under evaluation.

The first concrete device-selection change is interface **4**, alternate setting
**1**, alongside PID **0768**. Interface 0 on this device is USB audio, so changing
only the PID would claim the wrong interface.

  establish that count.

- No successful OUT completion has a length different from its matched submit.

## Protocol comparison

| Property | Existing smid | Submitted 0768 |
| --- | --- | --- |
| USB display interface / alternate | 0 / 1 | **4 / 1** |
| Bulk OUT | 0x02 | 0x02 |
| Interrupt OUT / IN | 0x01 / 0x81 | 0x01 / 0x81 |
| Packet marker | `smifalconsta` | identical |
| Display selectors | 0xa0000002 / 0xb0000002 | identical |
| Image command / codec | 0x0104 / 0xe0 | identical |
| Top rectangle / band marker | (0,0,1920,544) / 0x21 | identical |
| Lower rectangle / band marker | (0,536,1920,544) / 0x22 | identical |
| Framebuffer stride | 7,680 bytes | identical |
| JPEG | baseline, 8-bit, YUV420 | identical |
| Decoder trailer reservation | 0x5000 bytes | identical |

The descriptors and SET_INTERFACE request at record **684** both establish
interface 4/alternate 1. The USB tree reports **5000M**, not a USB 2 fallback.

The analyzer finds 207 pairs for selector A and 203 pairs for selector B across
the whole capture. All 820 image headers match the fields generated by
`smid_frame_header_build()`; the only byte differences are in bytes 43–47,
which the builder zeroes and does not otherwise define.

The original `smid_cnm_build_header_base()` recreates the first **0x1651 bytes**
of every captured decoder trailer exactly, when supplied with that packet's
captured JPEG slot length and captured base address. This validates the
structured decoder layout, Huffman/quantization tables, and JPEG parsing against
the capture. It does not validate smid's chosen base address on the new device.
Only 76/820 full 0x5000-byte reservations match byte for byte; all other
differences start at or after 0x1651, beyond the generated structured prefix.
Do not copy these trailing bytes into a driver or describe the entire trailer
as byte-identical.

The known-good 0760 reference capture has the same image shapes, selectors,
codec, and 0x5000 trailer reservation (617 images, no capture truncation).

## Initialization and acknowledgements

The main command families match: work mode, chip initialization, version,
topology, monitor creation, mode setting, source/layer binding, cursor commands,
and heartbeat. The first single-display mode at record **763** and final
dual-display mode at record **1127** match the corresponding smid mode payloads
(command and two mode slots, bytes 20–40).

The complete initialization sequences are not identical. In particular:

- Record **1019** sends command 0x4e, absent from smid's initialization.
- The vendor performs extra monitor/topology operations and an intermediate
  mode change at record **1063** before the final dual-display mode.
- Some command arguments differ; much surrounding vendor data also looks like
  uninitialized process memory. The capture does not establish which differing
  bytes are required. Do not replay arbitrary padding or infer that every byte
  difference needs a new device-specific command.

There are 174 observed 0x010001e9 acknowledgements for target A and 174
0x010101e9 acknowledgements for target B. An existing source issue is exposed by
these replies: `usb.c:rx_publish()` first tests
`(v & 0x00ffffffu) == 0x000001e9u`, which excludes the target-B bit that its
nested branch then tries to handle. Thus the B branch is unreachable for the
observed B replies. This is a source inspection finding; `verify_capture.py`
projects that predicate over the capture, rather than exercising USB I/O.
The development notes document the same A/B reply words for the original
adapter, so this is not evidence of a new 0768 acknowledgement format.

Before a test build, address that bug separately and verify both target cases.
Do not claim it explains the vendor driver's CPU usage.

## Host-side findings

- Kernel: 6.1.0-53-amd64.
- Two active 1920x1080 USB outputs plus the directly connected 2560x1440 output.
- `modinfo evdi` failed with `zsh: command not found: modinfo`; it did not return
  an EVDI version. Try `/usr/sbin/modinfo evdi` or `/sbin/modinfo evdi`.
- The reported driver is Intel iHD 23.1.1, advertising VA-API 1.17.
- JPEG encode (`VAProfileJPEGBaseline : VAEntrypointEncPicture`) is present.
- **VAProfileNone / VAEntrypointVideoProc is absent** from the supplied output.
  smid explicitly creates that configuration for BGRX-to-NV12 conversion.
  Confirm through the Intel DRM render node before predicting that the current
  direct-vaapi backend can initialize.

Intel's [23.1.1 feature table](https://github.com/intel/media-driver/blob/intel-media-23.1.1/README.md)
lists Skylake colour-space conversion in the full-feature build, but not the
free-kernel build. The installed package variant is therefore a plausible
explanation for missing VPP, **not confirmed by the submitted diagnostics**.
Debian provides [intel-media-va-driver-non-free 23.1.1](https://packages.debian.org/bookworm/intel-media-va-driver-non-free).
Check installed packages first; no installation change is prescribed here.
Intel documents [the VAProfileNone / VideoProc capability query](https://github.com/intel/libva/blob/master/va/va_vpp.h).

JPEG support alone also leaves YUV420 encode attributes, raw packed headers,
BGRX USER_PTR import, and actual conversion/encoding untested. Debian 12's
libusb version also needs checking: the current source uses
`libusb_init_context()`, introduced after stock bookworm's 1.0.26.

From the repository root, with Python 3.11+ and a C compiler:

```sh

  research/0768-20261018/generated/0768.json

  /home/je/Downloads/smi-0768.pcap.gz \
  research/0768-20261018/generated/0768-verification.json
gzip -dc /home/je/Downloads/smi-0768.pcap.gz | tcpdump -nn -r - --count
```

Pillow enables independent JPEG decoding in `verify_capture.py`; the JSON
explicitly reports whether it was available. Here it was available and decoded
all 820 images. The verifier compiles the existing C packet/decoder builders as
a local shared object, with no hardware access. It uses `-iquote` for repository
headers because `-I` would cause the project's `time.h` to shadow libc's header.
